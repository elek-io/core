# JSDoc findings

Every JSDoc finding phase 3 of [`jsdoc-review.md`](./jsdoc-review.md) produced, across all 92 non-test source files. Phase 4 burns this list down, serially, writing the `contributing/` and `docs/` sections the `overflows` rows ask for before the blocks that point at them.

No source was edited. The rows are analysis only, and a row's "what to do" describes the block phase 4 should write, calibrated against the Exemplar section of the review plan. Phase 3.5 verified and sorted the code findings, corrected the rows the commits after the analysis made false, and rewrote the escalations as five buckets.

Read [`../contributing/documentation.md`](../contributing/documentation.md) before acting on any row.

## How to read a row

`kind` is one of five. The bar for every row is that a reader is misled, or is missing something they need.

| Kind | Means |
| --- | --- |
| `missing` | no block on a symbol `jsdoc/documented-export` requires one for |
| `restates` | the block says only what the signature already says |
| `wrong` | the block contradicts what the code does |
| `stale` | the block describes behavior that has since changed |
| `overflows` | the explanation does not fit a block, and the doc that should hold it does not say it yet |

The 57 `missing` rows are exactly the 57 symbols the coverage rule reports with `src/documentation-baseline.json` ignored. Phase 3 did not hunt for more, it added the "what to do".

- `prose/punctuation` runs on `allMarkdownFiles` (`src/test/documentation.ts:746`), so an em dash in JSDoc passes while the same character fails in a doc. Five sites left, all confirmed: `src/schema/valueSchema.ts:166`, `src/service/ReferenceService.ts:561`, `src/astro/schema.ts:390`, `src/cli/generateTypesAction.ts:83` and `:170`. The sixth, `src/schema/valueSchema.ts:276`, went with the link URL fix, which is how a rule nobody enforces gets kept. Widen the rule to comment lines in `sourceFiles`, or say in `contributing/documentation.md` that JSDoc is out of its scope.
- `jsdoc/symbol-reference` runs on `sourceFiles` (`:1069`), so a wrong `Class.member` inside a `contributing/` doc is unchecked. `contributing/markdown-internals.md:12` puts `validateValueReferences` on `EntryService`. It lives on `ReferenceService` at `src/service/ReferenceService.ts:306`, the same misattribution `16cda50` fixed in the source.
- `jsdoc/documented-export` skips any exported const whose initializer is not a function (`:549`), so `astroDefaults` carries no block, is re-exported from `@elek-io/core/astro`, and will never reach the baseline.
- **New.** `boundaryMessage`, added in `e327d60`, strips a `ZodError`'s issue messages only inside `logBoundaryError`. Eleven direct `logService.warn` and `logService.error` calls interpolate a raw `error.message` with no such guard, among them `AbstractSlugIndexedEntityService.ts:196` and `:213` and `AbstractEntityService.ts:93`, `:108` and `:136`. None can carry a User's string today, because the entity file schemas produce zod defaults and Core's own static messages, but nothing asserts that and `logSweep.test.ts` drives service calls rather than these failure paths. #### `not-a-bug`

The claim does not reproduce, with what was found instead.

- **`NotFound` is documented and not thrown.** Fixed by `bfd111c`. `JsonFileService.readFile` answers a missing file with `CoreError.notFound` and `notFoundIfMissing` does the same for a missing directory, so a missing entity is `NotFound` rather than `Internal` and `errorContract.test.ts` asserts it. Pattern 3 above and the `src/service/EntryService.ts:191` row have been corrected. Phase 4 may write "throws `NotFound`" into an entity read block.
- **`datetime()` reachable from `GitTagService`'s parsing of git output.** It is not. `list()` computes `datetime(lineArray[6])` for every line, but a tag whose `%(*authordate)` is empty is a lightweight tag, which carries no `Type` trailer and is dropped by `isGitTag` before the value is returned. The falsy-guard defect is real and stays in `blocking`, reached through the public `datetime` export instead.
- **"The direct reads in `checkAsset` and `checkEntry` see the raw ENOENT."** They do not, and did not before `bfd111c` either. Both go through `this.jsonFileService.read` (`src/service/ReferenceService.ts:488` and `:534`), so the `ENOENT` branch of `isNotFoundError` is dead for its own callers.

#### The order to fix them in

1. ~~**The safety bucket.**~~ Done, all four plus the `JsonFileService` one found alongside them, each with a failing test first and the log sweep extended to the failure paths that let one of them recur.
2. **The one line fixes.** `refNameToTagName`, the `0` bound, the plain `Error`, `GitTagService.delete`'s guards, `elek()`'s handlers, `watchProjects`'s separator, `datetime`'s guard. Each is independent and each unblocks a row.
